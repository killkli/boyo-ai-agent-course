# 第 6 堂：辦公室場景工作坊

## 基本資訊

- **時長**：60 分鐘
- **型態**：分組實作 + Demo 分享 + 課程總結
- **對應學習目標**：6.1 將 Agent 技術應用於真實辦公室場景、6.2 完成從需求分析到 Agent 部署的完整流程、6.3 與團隊協作設計 Agent 解決方案、6.4 規劃個人的後續學習路徑

### 課前準備（講師用）

- 將學員分為 4 組（每組 3-5 人），每組至少有一台已安裝 Hermes 的筆電
- 準備四個場景說明卡（可印出或投影）
- 確認每組有穩定的網路連線
- 準備計時器（手機即可），控制各階段時間
- 準備「最佳創意獎」小獎品（增加趣味性和動力）

---

## 教學流程

### 第一階段：工作坊說明與分組（5 min）

**講授要點**

- 這是整門課的壓軸：把前五堂學到的知識，用在真實的辦公室場景
- 每組會拿到一個場景，需要：
  1. 分析需求（什麼工作要自動化？）
  2. 設計 Agent 方案（要用哪些工具？怎麼串起來？）
  3. 實際操作 Hermes 完成（至少做出可運作的原型）
  4. 準備 3 分鐘的成果 Demo
- 評分標準：不是看結果多完美，而是看思路是否清晰、是否善用工具、是否能說出改進方向

**分組方式**

- 依座位分組，每組 3-5 人
- 每組選出：組長（統籌）、操作員（負責打指令）、報告員（負責 Demo）
- 各組抽籤或協商選擇場景（A/B/C/D）

### 第二階段：分組實作（30 min）

各組拿到自己的場景說明卡後，開始實作。以下為四個場景的完整說明：

---

#### 場景 A：自動化每日報表彙整

**任務說明**

你是一個部門助理，每天早上需要從各組收集工作進度，彙整成一份日報給主管。目前流程：各組用 Email 或訊息回報進度 → 你手動複製貼上 → 排版 → 發送。這個流程每天花 40 分鐘，而且容易漏掉內容。

**目標**：設計一個 Hermes Agent，讓報表彙整流程自動化。

**建議使用的工具**

| 工具 | 用途 |
|------|------|
| `file_read` | 讀取各組提交的進度檔案 |
| `file_write` | 產生彙整後的日報檔案 |
| `scheduler` | 設定每天定時執行 |
| `web_search`（選配） | 查詢相關產業動態加入日報 |

**實作步驟提示**

1. **準備測試資料**：建立 3 個模擬的組別進度檔案
   ```bash
   mkdir -p ~/workshop-scenario-a
   ```
   建立 `team-alpha.txt`、`team-beta.txt`、`team-gamma.txt`，各放入模擬的工作進度內容。

2. **設計提示詞**：讓 Hermes 讀取所有檔案，按統一格式彙整
   ```
   請依序讀取以下檔案：
   - ~/workshop-scenario-a/team-alpha.txt
   - ~/workshop-scenario-a/team-beta.txt
   - ~/workshop-scenario-a/team-gamma.txt

   將內容彙整為一份日報，格式如下：
   # 日報 — [今天的日期]

   ## 各組進度
   ### [組名]
   - 本日完成：...
   - 進行中：...
   - 需協助：...

   ## 整體摘要
   [一段話總結今日重點]

   ## 待追蹤事項
   - ...

   將結果存到 ~/workshop-scenario-a/daily-report.md
   ```

3. **加入排程**：設定每天早上 9 點自動執行

**預期產出**

- 一份格式統一的日報 Markdown 檔案
- 一個排程設定（展示用即可）
- 能說明：如果要接上真實的 Email 收信，還需要哪些工具或整合

#### 場景 B：會議記錄整理與待辦追蹤

**任務說明**

你是一個專案經理，每周有 5-8 場會議，每次會議後需要整理會議記錄、標記行動項目（Action Items）、追蹤負責人和截止日期。目前用手動整理，容易遺漏待辦事項，也難以追蹤完成狀態。

**目標**：設計一個 Hermes Agent，自動整理會議記錄並產出結構化的待辦清單。

**建議使用的工具**

| 工具 | 用途 |
|------|------|
| `file_read` | 讀取會議記錄原始內容 |
| `file_write` | 產出整理後的會議記錄和待辦清單 |
| `web_search`（選配） | 查詢會議中提到的外部參考資料 |

**實作步驟提示**

1. **準備測試資料**：建立一份模擬的會議記錄
   ```bash
   mkdir -p ~/workshop-scenario-b
   cat > ~/workshop-scenario-b/meeting-raw.txt << 'EOF'
   產品週會 2026/05/21
   出席：小明、阿華、小美、老王

   小明：上週的登入頁改版已經上線，轉換率提升了 15%。下一個要處理的是結帳流程優化，預計下週三完成設計稿。

   阿華：後端 API 效能問題已經定位到是資料庫查詢沒加索引。修復計畫已經排入這週的 sprint，預計週四上線。不過需要小美幫忙確認前端呼叫方式是否需要調整。

   小美：前端沒問題，但阿華的 API 文件跟實際行為有出入，請在週三前更新文件。

   老王：客戶 A 反映報表匯出功能有問題，匯出超過 1000 筆會 timeout。這個要優先處理。

   結論：結帳流程設計稿下週三完成、API 修復本週四上線、API 文件週三前更新、報表匯出 bug 列為 P0 優先處理。
   EOF
   ```

2. **設計提示詞**：讓 Hermes 整理會議記錄，提取待辦事項
   ```
   請讀取 ~/workshop-scenario-b/meeting-raw.txt，進行以下整理：

   1. 產出一份格式化的會議記錄，包含：會議名稱、日期、出席者、討論內容摘要
   2. 提取所有行動項目（Action Items），格式：
      - [ ] 待辦事項描述 | 負責人 | 截止日期 | 優先級（P0/P1/P2）
   3. 如果有提到阻塞或依賴關係，額外標記出來

   將結果存到 ~/workshop-scenario-b/meeting-notes.md
   ```

3. **進階挑戰**（時間允許）：讓 Hermes 比較多份會議記錄，找出重複或衝突的待辦

**預期產出**

- 一份結構化的會議記錄
- 一份有負責人、截止日期、優先級的待辦清單
- 能說明：如果要持續追蹤待辦完成狀態，需要怎麼設計

#### 場景 C：客戶來信分類與回覆建議

**任務說明**

你是一個客服團隊主管，每天收到 30-50 封客戶來信，需要分類（詢問/客訴/建議/續約）、判斷優先級、並提供回覆建議給客服人員參考。目前完全依賴人工閱讀和分類，效率低且分類標準不一致。

**目標**：設計一個 Hermes Agent，自動分類客戶來信並產出回覆建議。

**建議使用的工具**

| 工具 | 用途 |
|------|------|
| `file_read` | 讀取模擬的客戶來信 |
| `file_write` | 產出分類結果和回覆建議 |
| `web_search`（選配） | 搜尋產品最新資訊以提供準確回覆 |

**實作步驟提示**

1. **準備測試資料**：建立 3 封模擬客戶來信
   ```bash
   mkdir -p ~/workshop-scenario-c
   cat > ~/workshop-scenario-c/email-01.txt << 'EOF'
   寄件者：張經理 (zhang@company-a.com)
   主旨：關於續約方案

   你好，
   我們公司的企業方案明年一月到期，想了解續約的方案和價格。
   目前使用人數大約 50 人，明年可能會增加到 80 人。
   另外，我們對你們新推出的 AI 分析功能很有興趣，續約時可以一起談嗎？

   張經理
   EOF

   cat > ~/workshop-scenario-c/email-02.txt << 'EOF'
   寄件者：李小姐 (li@gmail.com)
   主旨：URGENT 系統無法登入！

   你們的系統從今天早上開始就登不進去！！
   我嘗試了重設密碼、換瀏覽器、用手機都是一樣的問題。
   我有重要的報告今天下午要交，這樣我會開天窗！！
   請立刻幫我處理！！！

   李小姐
   會員編號：VIP-8821
   EOF

   cat > ~/workshop-scenario-c/email-03.txt << 'EOF'
   寄件者：王先生 (wang@startup.io)
   主旨：功能建議：批次匯出

   你好，
   我是你们产品的长期用户，有一个功能建议。

   目前匯出報表只能一次匯出一個月的資料，如果能支援自訂日期區間的批次匯出會更方便。
   我每季需要匯出整季的資料給投資人，現在要分三次匯出再合併，很麻煩。

   另外，匯出格式如果能支援 Excel 會更好，目前只有 CSV。

   謝謝考慮！
   王先生
   EOF
   ```

2. **設計提示詞**：讓 Hermes 批次分類並建議回覆
   ```
   請依序讀取以下三封信件：
   - ~/workshop-scenario-c/email-01.txt
   - ~/workshop-scenario-c/email-02.txt
   - ~/workshop-scenario-c/email-03.txt

   對每封信進行：
   1. 分類（詢問/客訴/建議/續約）
   2. 優先級判斷（緊急/高/中/低）
   3. 情緒判斷（正面/中性/負面/憤怒）
   4. 回覆建議（包含建議的回覆主旨和內容重點，不寫完整回覆，只列重點）

   將結果整理成表格格式，存到 ~/workshop-scenario-c/classification.md
   ```

**預期產出**

- 一份信件分類表格（分類、優先級、情緒、回覆重點）
- 每封信的回覆建議大綱
- 能說明：如果要整合真實的 Email 信箱，需要怎麼做 API 串接

#### 場景 D：專案進度監控與異常提醒

**任務說明**

你是一個 PMO（專案管理辦公室）成員，負責監控 3 個進行中專案的進度。每週需要彙整各專案狀態、識別落後或風險項目、並主動通知相關人員。目前用試算表手動追蹤，容易漏掉即將逾期或已經落後的任務。

**目標**：設計一個 Hermes Agent，自動分析專案進度並標記異常。

**建議使用的工具**

| 工具 | 用途 |
|------|------|
| `file_read` | 讀取各專案的進度資料 |
| `file_write` | 產出監控報告和異常清單 |
| `scheduler` | 設定每週定時檢查 |
| `web_search`（選配） | 查詢專案相關的外部風險因素 |

**實作步驟提示**

1. **準備測試資料**：建立 3 個模擬專案的進度檔案
   ```bash
   mkdir -p ~/workshop-scenario-d
   cat > ~/workshop-scenario-d/project-alpha.txt << 'EOF'
   專案：Alpha（客戶門戶重構）
   PM：小明
   預計完成日：2026-06-30
   進度：65%

   里程碑：
   [完成] 需求訪談 — 原訂 4/15，實際 4/14
   [完成] UI 設計 — 原訂 5/01，實際 5/03
   [進行中] 前端開發 — 原訂 5/20，目前進度 80%
   [未開始] 後端 API — 原訂 6/01
   [未開始] 整合測試 — 原訂 6/15
   [未開始] 上線部署 — 原訂 6/30

   風險：後端 API 尚未開始，且前端開發輕微落後，可能壓縮到後端時程。
   EOF

   cat > ~/workshop-scenario-d/project-beta.txt << 'EOF'
   專案：Beta（內部報表自動化）
   PM：阿華
   預計完成日：2026-06-15
   進度：45%

   里程碑：
   [完成] 資料盤點 — 原訂 4/20，實際 4/25（落後 5 天）
   [完成] ETL 流程設計 — 原訂 5/05，實際 5/10（落後 5 天）
   [進行中] 報表開發 — 原訂 5/25，目前進度 30%
   [未開始] 使用者測試 — 原訂 6/01
   [未開始] 正式上線 — 原訂 6/15

   風險：已經連續兩個里程碑落後，目前進度 45% 但時間已過 60%。如果不調整時程或資源，很可能無法如期上線。
   EOF

   cat > ~/workshop-scenario-d/project-gamma.txt << 'EOF'
   專案：Gamma（行動 App 開發）
   PM：小美
   預計完成日：2026-07-31
   進度：35%

   里程碑：
   [完成] 需求定義 — 原訂 4/30，實際 4/28
   [完成] 技術架構 — 原訂 5/10，實際 5/09
   [進行中] 核心功能開發 — 原訂 6/15，目前進度 40%
   [未開始] UI/UX 優化 — 原訂 7/01
   [未開始] Beta 測試 — 原訂 7/15
   [未開始] 正式上架 — 原訂 7/31

   風險：目前進度正常，無重大風險。但 App Store 審核時間可能影響上架日期，建議提前一週提交。
   EOF
   ```

2. **設計提示詞**：讓 Hermes 分析進度並標記異常
   ```
   請讀取以下三個專案的進度檔案：
   - ~/workshop-scenario-d/project-alpha.txt
   - ~/workshop-scenario-d/project-beta.txt
   - ~/workshop-scenario-d/project-gamma.txt

   進行以下分析：

   1. **進度健康度評估**：比較每個專案的「時間消耗比例」vs「完成比例」
      - 健康：完成比例 >= 時間消耗比例
      - 注意：完成比例略低於時間消耗比例（差距 < 10%）
      - 警告：完成比例明顯落後（差距 >= 10%）
      - 危險：已有多個里程碑落後

   2. **異常清單**：列出所有需要關注的項目，標明原因和建議行動

   3. **風險摘要**：綜合判斷哪些專案可能無法如期完成

   將結果存到 ~/workshop-scenario-d/status-report.md
   ```

**預期產出**

- 一份專案健康度儀表板（用 Markdown 表格呈現）
- 一份異常清單（專案 Beta 顯然是重點）
- 具體的建議行動（例如：建議專案 Beta 增加 1 名後端工程師或延後上線日期）
- 能說明：如果要即時監控而不是每週彙整，架構需要怎麼調整

### 第三階段：各組 Demo 與分享（15 min）

**流程**

- 每組 3 分鐘 Demo + 1 分鐘 Q&A（4 組共 16 分鐘，預留彈性）
- Demo 內容建議包含：
  1. 場景是什麼？為什麼選這個場景？
  2. 設計了什麼 Agent 方案？（用了哪些工具）
  3. 實際展示 Hermes 的操作過程和產出結果
  4. 遇到了什麼問題？怎麼解決的？（或還沒解決）
  5. 如果有更多時間，會怎麼改進？

**講師回饋重點**

- 肯定每組的創意和實作成果
- 指出可以改進的地方（用建設性的方式）
- 特別點出不同組之間的思路差異，讓全班學到更多觀點
- 連結回課程概念：「你們剛才做的，就是把 Model + Harness + Tools + Memory 組合起來解決真實問題」

**互動評比**

- 全班投票選出「最佳創意獎」（不能用自己組）
- 獲獎組別可獲得小獎品

### 第四階段：課程總結與後續學習路徑（10 min）

**課程回顧**

用一頁投影片快速回顧六堂課的重點：

| 堂數 | 主題 | 核心收穫 |
|------|------|---------|
| 第 1 堂 | AI 基礎與 Agent 概論 | AI、ML、LLM 的關係；Agent 不等於 Chatbot |
| 第 2 堂 | Model 與 Prompt 工程 | 模型選擇考量；Prompt 是 Agent 的控制介面 |
| 第 3 堂 | Harness 控管框架 | 為什麼需要 Harness；狀態管理、錯誤處理、權限控制 |
| 第 4 堂 | Agent 解剖學 | 四要素、工具風格、記憶機制、安全防線、反模式 |
| 第 5 堂 | Hermes 實作 | 安裝、操作、工具啟用、自學習迴圈 |
| 第 6 堂 | 辦公場景工作坊 | 把所學用在真實場景，完成端到端實作 |

**後續學習路徑**

講師提供三條路徑供學員依興趣選擇：

**路徑一：辦公室應用深化（適合：想在工作中導入 Agent 的人）**

1. 回到工作崗位後，挑一個自己的重複性任務，用 Hermes 建立自動化
2. 學習進階工具整合：Email API、試算表讀寫、企業通訊軟體 Bot
3. 建立個人化的工具庫，累積自己的 Agent 技能集
4. 推薦資源：Hermes 官方文件的工具整合章節

**路徑二：Agent 開發入門（適合：想自己開發 Agent 的人）**

1. 學習 Python 基礎（如果還不會的話）
2. 深入研究 Hermes 的工具註冊系統，練習自製工具
3. 了解 LangChain / CrewAI 等其他 Agent 框架，比較設計理念
4. 推薦資源：Hermes GitHub repo 的 examples 資料夾、LangChain 官方教學

**路徑三：AI Agent 策略與管理（適合：管理職、決策者）**

1. 了解企業導入 AI Agent 的評估框架（ROI、風險、合規）
2. 研究不同產業的 Agent 應用案例
3. 建立組織的 AI 使用規範和安全政策
4. 推薦資源：McKinsey / Gartner 的 AI Agent 產業報告

- 建議學員訂閱 AI Agent 相關電子報，持續追蹤產業動態

**結語**

> 「今天你們不只是學了一個工具，而是學會了一種新的工作方式。AI Agent 不是要取代你，而是要成為你的超強助手。關鍵在於：你能不能清楚定義問題、設計好的流程、並善用工具去執行。這些能力，才是 AI 時代最值錢的技能。」

## 關鍵概念

| 概念 | 一句話解釋 |
|------|-----------|
| 場景化設計 | 從真實工作痛點出發，設計 Agent 解決方案 |
| 工具組合 | 把多個工具串接起來，完成複雜的工作流程 |
| 原型思維 | 先做出最小可運作版本，再迭代改進 |
| 團隊協作 | 分工合作：有人分析需求、有人操作 Agent、有人整理成果 |
| 迭代改進 | Agent 方案不是一次到位，需要持續調整優化 |
| 後續學習路徑 | 根據個人目標（應用/開發/管理），選擇不同的深化方向 |

---

## 教學提示

1. **分組實作時，講師和助教要主動巡場**：每組可能卡在不同的地方。最常見的卡點是：提示詞不知道怎麼寫、工具不知道選哪個、Hermes 報錯不知道怎麼辦。每隔 5-7 分鐘巡一圈，主動詢問「有遇到什麼問題嗎？」

2. **場景 D（專案監控）難度最高**：因為需要跨多個檔案做比較分析。如果某組程度較弱，建議引導他們先專注在一個專案的分析，不要一次處理三個。

3. **Demo 環節控制時間**：學員容易超時。準備一個明確的時間信號（舉手或按鈴），1 分鐘前提醒，時間到就切換。如果某組的 Demo 特別精彩，可以在所有組都展示完後再回來多問幾個問題。

4. **成果不完美是正常的**：30 分鐘能做到「可運作的原型」就很棒了。不要讓學員追求完美，而是鼓勵他們說出「如果有更多時間會怎麼改進」。這個思考過程比成品更有價值。

5. **課程總結要有情感**：學員剛完成一個密集的 6 小時課程，最後的總結要讓他們覺得「我做到了、我學到了、我有一個可以帶回去用的東西」。用具體的場景成果來證明，而不是空泛的鼓勵。

6. **後續學習路徑要具體**：不要只說「繼續學習」，要給明確的下一步（看什麼文件、做什麼練習、加入什麼社群）。

## 延伸活動（若有餘裕時間）

### 跨組合作挑戰

如果有額外 10-15 分鐘，讓不同場景的組別交流：

- 場景 A（報表彙整）+ 場景 D（專案監控）：能不能讓報表 Agent 也做進度監控？
- 場景 B（會議記錄）+ 場景 C（客戶來信）：能不能讓會議記錄的自動整理技巧，也用在客戶來信分類？

這個活動的重點是讓學員思考：Agent 方案不是孤立的，不同的能力可以組合出更強大的解決方案。

### 一句話電梯簡報

每位學員用一句話（30 秒）回答：「如果回到公司，你會怎麼跟主管說明今天學到了什麼？」

這個活動幫助學員把課程收穫內化為自己的語言，也練習在職場中推廣 AI Agent 的溝通能力。

# Lab 4：辦公室場景實作（一）— 從需求到原型

## 基本資訊

- **所屬課程**：Hermes Agent 全天實作工作坊
- **Lab 編號**：Lab 4
- **時長**：60 分鐘
- **型態**：分組實作
- **位置**：下午場第一個單元
- **銜接關係**：承接上午的 Hermes 安裝、工具使用與自動化流程練習，為 Lab 5 的迭代優化建立第一版原型
- **核心目標**：讓學員把一個真實辦公室情境拆成可執行的需求，完成資料準備、流程設計與第一版可運作原型

## 分組與場景選擇

- 全班分為 4 組，每組 4–6 人
- 每組固定三個角色，必要時可一人兼任兩項：
  - **流程整理者**：負責釐清需求、整理工作步驟
  - **Hermes 操作員**：負責輸入任務、觀察 Agent 行為
  - **記錄與報告者**：負責記錄決策、整理 Demo 素材
- 四組各選一個場景，原則上 A／B／C／D 各一組，避免重複
- 若現場人數不足四組，可由講師指定不同小組處理同一場景的不同版本，例如「基礎版」與「進階版」

### 場景分配原則

| 場景 | 主題 | 建議對象 | 核心能力 |
|------|------|----------|----------|
| A | 自動化每日報表彙整 | 想先從固定格式任務開始的小組 | 彙整、摘要、格式統一 |
| B | 會議記錄整理與待辦追蹤 | 熟悉跨段文字整理的小組 | 摘要、結構化、行動項目擷取 |
| C | 客戶來信分類與回覆建議 | 對客服或業務情境有感的小組 | 分類、判斷優先級、回覆建議 |
| D | 專案進度監控與異常提醒 | 想挑戰分析型任務的小組 | 比對、風險判讀、異常標記 |

## 教學流程

| 時間 | 階段 | 講師任務 | 學員任務 |
|------|------|----------|----------|
| 0–5 分鐘 | 任務說明與分組確認 | 說明本 Lab 目標、交付標準與時間限制 | 確認組員分工與場景 |
| 5–15 分鐘 | 需求分析 | 引導小組聚焦「誰在用、要解決什麼、成功長怎樣」 | 拆解流程、定義輸入與輸出 |
| 15–20 分鐘 | 測試資料準備 | 提醒資料要夠小、夠真實、夠能驗證 | 準備範例資料或整理既有素材 |
| 20–50 分鐘 | 第一版原型實作 | 巡場協助、提醒先求可運作 | 用 Hermes 完成第一版流程 |
| 50–60 分鐘 | 結果檢查與收斂 | 要求每組留下可展示的成果 | 整理原型、記錄問題與下一步 |

### 本 Lab 的交付標準

每組在 60 分鐘結束前，至少要交出以下三項：

1. 一句話說清楚這個場景要解決的工作問題。
2. 一份可展示的第一版原型成果。
3. 一張簡短說明，列出輸入資料、處理步驟、輸出結果。

## 四個場景的操作指引

這四個場景的重點很一致：先把需求講清楚，先做出可運作版本。做完第一版後，再把還沒處理好的地方留給下一輪迭代。

### 場景 A：自動化每日報表彙整

#### 場景目標

把多位同事分散提交的進度內容，整理成主管可以快速閱讀的日報。重點不是做得很漂亮，而是先讓格式一致、重點清楚、遺漏變少。

#### 建議拆解方式

- 使用者是誰：主管、部門助理
- 輸入是什麼：不同組別或同事的進度文字
- 輸出是什麼：一份統一格式的日報
- 成功標準：能快速看出已完成事項、進行中事項、需要協助事項

#### 實作重點

1. 先決定日報欄位，不要一開始就追求排版。
2. 讓 Hermes 先做「彙整」，再做「摘要」，不要一次塞太多要求。
3. 若內容來源差異很大，先要求 Agent 按相同欄位重新整理，再合併。
4. 若時間還夠，再補上整體摘要與待追蹤事項。

#### 第一版原型最低要求

- 至少能整合 3 份進度內容
- 產出固定格式的日報
- 能看出各組進度差異

#### 講師可追問的方向

- 這份日報是寫給誰看的？
- 主管最想先看到哪一欄？
- 如果有一組沒有交資料，原型要怎麼處理？

### 場景 B：會議記錄整理與待辦追蹤

#### 場景目標

把散亂的會議紀錄轉成兩種成果：一份能回顧脈絡的摘要，一份能追蹤責任與時程的待辦清單。

#### 建議拆解方式

- 使用者是誰：專案經理、會議主持人、團隊成員
- 輸入是什麼：逐字或半逐字的會議內容
- 輸出是什麼：會議摘要、Action Items、阻塞事項
- 成功標準：讀完後知道誰要做什麼、何時完成、卡在哪裡

#### 實作重點

1. 先區分「討論內容」與「需要追蹤的行動項目」。
2. 要求 Hermes 為每個待辦補上負責人、期限、優先順序。
3. 若原始紀錄沒有明確期限，可要求 Agent 標示「待確認」，不要假設。
4. 若時間允許，可再加上依賴關係或風險提醒。

#### 第一版原型最低要求

- 產出一份結構化會議摘要
- 至少整理出 3 項可追蹤待辦
- 標出負責人與截止時間是否明確

#### 講師可追問的方向

- 哪些內容算決議，哪些只是討論？
- 如果會議裡有人口語表達不完整，Agent 要不要直接補齊？
- 這份清單要給誰追蹤？格式要多細？

### 場景 C：客戶來信分類與回覆建議

#### 場景目標

讓 Hermes 幫忙做第一輪信件分流，先分清楚類型、緊急程度與回覆方向，減少客服人員從零開始判讀的時間。

#### 建議拆解方式

- 使用者是誰：客服、業務、客戶成功團隊
- 輸入是什麼：客戶信件或訊息內容
- 輸出是什麼：分類結果、優先級、回覆建議
- 成功標準：團隊看到結果後，能決定誰先處理、怎麼回

#### 實作重點

1. 先定義分類標籤，不要讓 Agent 自己發明太多類別。
2. 優先級規則要講清楚，例如影響登入、付款、續約的情況是否要提高處理等級。
3. 回覆建議先寫重點，不必一開始就生成完整信件。
4. 若同時處理多封信，要求輸出用表格或固定欄位，方便比較。

#### 第一版原型最低要求

- 至少處理 3 封不同類型來信
- 每封信都有分類與優先級判斷
- 每封信都有可供人工參考的回覆重點

#### 講師可追問的方向

- 哪一類信件最不能判錯？
- 如果客戶語氣很急，但問題其實不嚴重，優先級要怎麼定？
- 哪些內容應該交給人工最後確認？

### 場景 D：專案進度監控與異常提醒

#### 場景目標

把各專案狀態整理成一份能快速辨識風險的監控結果。這個場景的重點是比較，不只是摘要。

#### 建議拆解方式

- 使用者是誰：PM、PMO、部門主管
- 輸入是什麼：多個專案的進度資料、里程碑狀態、風險描述
- 輸出是什麼：健康度判斷、異常清單、提醒建議
- 成功標準：能一眼看出哪個專案需要先處理

#### 實作重點

1. 先訂健康度規則，例如正常、注意、警示、危險。
2. 要求 Hermes 說明判斷原因，避免只丟結論。
3. 先做單次分析，不必急著做成完整監控系統。
4. 若資料量偏大，先只處理 2–3 個專案，確保比較邏輯成立。

#### 第一版原型最低要求

- 至少比較 2 個以上專案
- 每個專案都有狀態判斷
- 至少列出 1 份異常清單或風險摘要

#### 講師可追問的方向

- 這個專案為什麼被判成警示？依據是什麼？
- 如果進度百分比看起來正常，但里程碑延遲，原型能不能辨識？
- 主管看到這份結果後，下一步會做什麼？

## 講師巡場提示

### 第一次巡場：需求有沒有收斂

觀察每組是否已回答下面三題：

- 這個場景的使用者是誰？
- 他每天或每週卡在哪個重複工作？
- 第一版原型只要做到什麼程度就算完成？

若小組還在空談概念，講師要把他們拉回來，請他們直接寫出「輸入 → 處理 → 輸出」。

### 第二次巡場：原型有沒有做小

常見問題是一次想做太多。講師可直接提醒：

- 先處理少量資料，確認流程通了再擴大
- 先做單輪任務，不急著加排程、自動通知或外部整合
- 先把欄位訂清楚，不要一直改格式

### 第三次巡場：結果能不能展示

最後 10 分鐘，講師要確認每組至少有以下內容可 Demo：

- 一份輸入資料
- 一次 Hermes 的處理結果
- 一句話說明這版原型解決了什麼
- 一句話說明下一輪最想補什麼

## 預期產出

每組在本 Lab 結束時，應留下以下成果：

- 一份場景需求摘要
- 一版可運作的 Hermes 原型成果
- 一份簡單流程圖或條列說明，描述資料如何進來、如何被處理、最後輸出什麼
- 一份供下一個 Lab 使用的迭代清單

| 項目 | 內容 |

| 輸入資料 | 原始文字、會議紀錄、信件或專案資料 |

## 關鍵概念

| 概念 | 說明 |
|------|------|
| 需求分析 | 先釐清使用者、痛點、輸入與輸出，再開始操作 Agent |
| 原型思維 | 第一版只求可運作，不求一步到位 |
| 結構化輸出 | 先把欄位定清楚，後續才容易比較、追蹤與擴充 |
| 工具選擇 | 根據任務需求決定是否需要讀檔、寫檔、搜尋或排程 |
| 驗證標準 | 原型好不好，不是看字數多寡，而是看能不能支援真實工作判斷 |
| 迭代準備 | 留下問題清單，才能在下一個 Lab 有方向地優化 |

## 教學提示

1. **把焦點放在需求，不要急著拚功能。** 很多學員一拿到場景就想直接叫 Hermes 做事，結果做到一半才發現輸入資料不清楚。
2. **先做最小版本。** 例如場景 A 先整 3 份日報、場景 B 先抓 3 個待辦、場景 C 先分類 3 封信、場景 D 先比較 2 個專案，流程通了再加料。
3. **提醒學員保留人工判斷。** 尤其是回覆建議、優先級判斷、風險分級，這些結果都應該能被人快速覆核。
4. **不要讓小組把時間耗在格式微調。** 這個 Lab 的重點是從需求走到原型，不是做出最漂亮的文件。
5. **把卡點當成教材。** 若某組卡在資料混亂、提示不清或結果不穩，這正好可以用來說明為什麼需求拆解和欄位定義很重要。
6. **為 Lab 5 留白。** 如果學員問能不能加排程、加通知、加更細的規則，講師可以先肯定想法，再提醒那些是下一輪迭代的工作。

## 與全天工作坊的連結

- 上午的 Lab 1–3 讓學員學會 Hermes 的基本操作、工具使用與自動化觀念。
- 這一個 Lab 要把前面學到的能力收斂成真實場景的第一版原型。
- 下一個 Lab 5 會直接接手這裡的成果，繼續做優化、補規則、處理例外情況。
- 因此本單元最重要的不是做完全部功能，而是留下一個清楚、可驗證、可續做的起點。

# Lab 5：辦公室場景實作（二）— 迭代與優化

## 基本資訊

- **時長**：50 分鐘
- **型態**：分組實作
- **定位**：Hermes Agent 全天實作工作坊下午場第二個 Lab
- **承接前一單元**：延續 Lab 4 的四個辦公室場景原型，針對第一版成果做迭代、補強與驗證
- **對應學習目標**：
  - 改善提示詞，讓 Agent 更穩定地完成多步驟任務
  - 依場景調整工具配置，縮小能力與權限的落差
  - 處理缺資料、格式不一致與其他例外情況
  - 在原型上加入進階功能，為最後 Demo 做準備

---

## 課前準備

### 學員準備

- 開啟上一個 Lab 完成的場景資料夾與原型輸出
- 整理一份「目前版本已知問題」清單，至少寫下 2 項
- 指定一位組員負責記錄本次改動內容，方便最後 Demo 說明

## 教學流程

### 第一階段：回顧 Lab 4 與盤點問題（5 分鐘）

**操作重點**

- 這一個 Lab 不追求重做，而是針對既有原型做有目的的修正
- 先確認「哪裡會失敗」，再決定「要改哪裡」
- 若第一版只能在理想資料下運作，還不能算完成

**各組任務**

1. 回看 Lab 4 的輸出結果
2. 用一句話描述原型目前最不穩定的地方
3. 選出本組這一輪最優先要改善的 1-2 個問題

---

### 第二階段：提示詞迭代（12 分鐘）

聚焦改善 Agent 的指令結構，讓輸出更穩定、可驗證。

**優化方向說明**

- 提示詞要把任務拆成明確步驟，而不是只給最後目標
- 先定義輸入、處理規則、輸出格式，再補上例外處理要求
- 若要比較多份資料，應要求 Agent 先逐份整理，再做總結
- 若要產出可驗證結果，需指定欄位、排序規則、缺漏標記方式

**建議優化方向**

- 補上欄位定義，例如日期格式、優先級分類、摘要長度
- 補上失敗處理，例如「若資料缺漏請標記待確認，不要自行猜測」
- 補上輸出限制，例如「先列異常，再列一般項目」
- 補上檢查步驟，例如「完成前再核對是否遺漏負責人與截止日」

---

### 第三階段：工具配置調整（10 分鐘）

讓工具組合更貼近任務需要，避免工具過多或過少。

**優化方向說明**

- 不是工具越多越好，要看流程是否真的需要
- 若任務只處理本機資料，就不一定要開啟外部搜尋
- 若任務要定期執行，才需要排程工具
- 工具配置要與權限、風險、可追蹤性一起考慮

**各組檢查問題**

- 目前是否有工具其實沒有用到？
- 是否缺少讓流程穩定落地的工具？
- 哪些步驟適合交給工具，哪些步驟應保留人工確認？
- 如果要 Demo，哪個工具最能清楚呈現價值？

---

### 第四階段：各場景的進階挑戰（15 分鐘）

各組依照自己的場景，從下列挑戰中至少完成 1 項。

#### 場景 A：課輔中心週報彙整

**進階挑戰**

- 加入異常偵測，標出未回報進度的課輔班、格式不一致或學童連續缺席的狀況
- 讓週報分成「教育處摘要版」與「各中心細節追蹤版」兩層輸出
- 增加跨週比較，指出與前一週相比的進度變化與學童出席趨勢

**迭代提示**

- 要求 Agent 分開處理「彙整各中心進度」與「判斷例外情況」兩件事
- 若某個課輔班未提供資料，輸出中要明確標示「缺資料，請聯繫該班老師」
- 學童連續缺席超過兩週的案件要自動標記為高優先追蹤

#### 場景 B：教學會議記錄整理與待辦追蹤

**進階挑戰**

- 比較多場教學研討會記錄，找出重複待辦、矛盾的教學指示或逾期未處理的個案
- 將待辦依負責人（教學組長、課輔老師、社工師、特教老師）、優先級或截止日重新排序
- 額外抽出需要持續追蹤的學童個案清單，標記各案的負責社工與下次檢討日期

**迭代提示**

- 要求 Agent 區分「決議」「待辦」「討論中但未定案」三種內容
- 若會議紀錄沒有明確截止日，要標示「待補」，不要自行推測
- 學童個案的後續追蹤要標明負責的專業人員（社工師或特教老師）

#### 場景 C：學童家長來信分類與回覆建議

**進階挑戰**

- 加入情緒強度判斷，優先標記涉及學童安全或家長情緒焦慮的高風險來信
- 區分「需要社工立即處理」與「可先內部確認後再回覆」兩類案件
- 將回覆建議拆成「社工可直接使用」與「需主管或特教老師審核」兩層

**迭代提示**

- 分類標準要固定（課程詢問、學童狀況反映、家長求助、資源申請、感謝回饋），避免同類型信件出現不同判斷
- 若信件資訊不足，回覆建議要先列出需補問事項
- 涉及學童身心安全的信件一律標記為最高優先級，不可降級

#### 場景 D：課輔計畫進度監控與異常提醒

**進階挑戰**

- 建立風險分級，區分注意、警告、危險三個層級，並為每個層級定義明確的判準
- 加入里程碑落後判斷，提示最需要先處理的課輔計畫（暑期密集課輔、數位學習推廣、特教早療）
- 產出「給教育處主管看的摘要」與「給各計畫負責人的行動清單」兩種版本

**迭代提示**

- 要求 Agent 先整理事實（進度百分比、里程碑狀態、資源使用），再做風險判斷
- 若資料中的日期或進度不完整，必須在報告中標示限制
- 人力缺口問題（如特教老師產假、英語師資不足）要特別標記為影響計畫執行的關鍵風險

---

### 第五階段：測試與驗證（5 分鐘）

這一段要確認優化後的版本，不只看起來比較完整，也真的比較穩定。

**驗證重點**

- 換一筆資料後（例如換一個課輔中心的進度、另一封家長來信），輸出格式是否仍一致
- 面對缺欄位、格式混亂或內容衝突時，是否有明確處理方式
- 進階功能是否真的有產出新資訊，而不是只換一種說法
- 組員是否能解釋每一項修改的理由
- 學童相關資訊的判斷結果是否準確，不可有誤判優先級的狀況

**建議驗證方式**

1. 每組至少加入 1 個邊界情況測試
2. 再跑一次原型流程
3. 比較優化前後差異
4. 記錄仍未解決的問題，留到 Demo 說明

---

## Demo 準備

請各組在最後 3-5 分鐘同步整理以下內容，避免下一個單元才臨時回想。

- 場景與原始需求是什麼
- Lab 4 版本最主要的問題是什麼
- 這次做了哪些迭代
- 哪一項改動最能提升實用性
- 有哪些邊界情況已處理，哪些還沒處理
- 如果再多 30 分鐘，下一步會補哪個功能

**建議 Demo 呈現順序**

1. 先說原型任務
2. 再說本輪優化重點
3. 展示優化後輸出
4. 補充測試結果與限制

---

## 自我檢查

完成本 Lab 後，各組至少應具備以下成果：

- 一份優化後的場景方案
- 一版更清楚、可重複使用的提示詞
- 一組較合理的工具配置說明
- 至少 1 個邊界情況處理策略
- 至少 1 項進階功能成果
- 一份可供下一單元 Demo 使用的重點筆記

---

## 關鍵概念

| 概念 | 說明 |
|------|------|
| 迭代 | 不重做整套流程，而是針對失敗點逐步修正 |
| 提示詞穩定性 | 指令是否能在不同資料條件下維持一致輸出 |
| 工具配置 | 依任務需求選擇合適工具，避免過度開權限 |
| 邊界處理 | 面對缺資料、格式錯誤、衝突資訊時的應對方式 |
| 可驗證輸出 | 讓人能快速檢查結果是否完整、正確、有依據 |
| 進階功能 | 在基本原型可運作後，增加更貼近真實工作的能力 |

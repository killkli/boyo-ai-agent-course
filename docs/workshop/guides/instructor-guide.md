# 講師手冊 — Hermes Agent 全天實作工作坊

> 供講師與助教於授課前、中、後使用。這份手冊對應的是 6 小時全天實作工作坊，不是原本六堂課拆分版的授課節奏。

---

## 一、基本定位

### 課程定位

這門課是「Hermes Agent 全天實作工作坊」，核心目標不是把概念講完整，而是讓學員在一天內完成安裝、操作、組裝工具、建立自動化流程，最後做出一個可展示的辦公室場景原型。

### 與原六堂課的差異

| 項目 | 原六堂課 | 全天工作坊 |
|------|----------|------------|
| 節奏 | 概念講授與實作分散 | 實作密度高，上午建技能、下午做場景 |
| 講師角色 | 以講解與示範為主 | 以帶操作、控節奏、排障、收斂成果為主 |
| 學員任務 | 逐堂吸收概念 | 當天就要產出可運作原型 |
| 時間壓力 | 每堂課相對單純 | 同一天要完成安裝、練習、分組、Demo |

### 講師的三個主要任務

1. 讓多數學員在上午完成基本操作，不被環境問題拖住。
2. 讓下午各組都能交出最小可展示成果，不追求功能做滿。
3. 讓學員帶著一套能延伸回工作現場的做法離開教室。

## 二、課前準備

### 2.1 講師與助教分工

建議至少配置 1 位主講師與 1 位助教；若學員超過 20 人，最好有第 2 位助教。

| 角色 | 主要工作 |
|------|----------|
| 主講師 | 控節奏、講解關鍵概念、做公開 Demo、決定何時收斂 |
| 助教 | 巡場排障、處理安裝與 API 問題、協助落後學員跟上 |
| 第二助教（選配） | 專門支援網路、帳號、模型設定等環境問題 |

### 2.2 設備與場地確認

- 投影畫面要能清楚看到終端機文字。
- 講師電腦字體建議放大到後排看得清楚的程度。
- 現場網路要先測，並準備手機熱點備援。
- 插座與延長線要夠，避免下午電力不足影響實作。
- 若場地允許，學員分組座位一開始就排好，省去下午重新移動時間。

### 2.3 帳號與資料準備

- 預先準備 2～3 組備用 API Key，給卡在註冊或額度不足的學員暫時使用。
- 準備四組辦公室場景資料包，避免下午各組花太多時間找素材。
- 準備一份講師自己的乾淨示範環境，避免 Demo 時混入舊設定。
- 準備一份「已安裝完成」備用環境，給完全卡住的學員接續操作。

### 2.4 課前通知建議

課前通知要明確，至少包含以下內容：

- 本課為全天 Hands-on 實作課，不建議只帶平板。
- 學員需具備基本終端機操作能力。
- 請先申請可用的 API Key。
- 若公司網路有限制，建議自備手機熱點。
- 請預留整天時間，中途離場會直接影響下午分組產出。

### 2.5 講師課前檢查清單

#### 課前一週

- [ ] 確認學員名單與人數。
- [ ] 發送課前準備信。
- [ ] 測試場景資料包是否完整。
- [ ] 確認講師示範流程能在乾淨環境跑完。

#### 課前一天

- [ ] 再跑一次全天示範路線。
- [ ] 檢查 API 額度與備援帳號。
- [ ] 準備投影片、教材連結、回饋表單。
- [ ] 整理常見錯誤對照表，方便助教快速排障。

#### 當天開課前

- [ ] 提前至少 30 分鐘進場。
- [ ] 測試投影、網路、電源與音訊。
- [ ] 開好講師示範所需視窗與檔案。
- [ ] 和助教確認巡場分區與求救手勢。

## 三、全天流程控管

### 3.1 全天節奏原則

這門課的節奏重點是「快速建立共同底線，盡早進入操作，下午集中產出」。講師不要把上午變成概念課，也不要把下午變成自由摸索時間。

### 3.2 各時段控管重點

| 時段 | 單元 | 講師任務 | 控管重點 |
|------|------|----------|----------|
| 09:00–09:25 | 開場與環境確認 | 說明目標、確認設備、完成分組 | 25 分鐘內一定要開始第一個操作 |
| 09:25–10:10 | Lab 1 | 帶完安裝與第一次任務 | 不讓少數人的安裝問題拖住全班 |
| 10:20–11:10 | Lab 2 | 帶工具使用與安全邊界 | 強調工具不是越多越好 |
| 11:20–12:10 | Lab 3 | 帶自動化流程與自學習觀察 | 上午結束前要讓學員看到「可重複」價值 |
| 13:10–14:10 | Lab 4 | 帶各組從需求走到原型 | 先求能跑，再求完整 |
| 14:20–15:10 | Lab 5 | 帶各組迭代優化 | 幫各組收斂範圍，避免越做越散 |
| 15:20–16:00 | Lab 6 | 發布挑戰與限時整合 | 挑戰是加分題，不可拖垮主線成果 |
| 16:10–16:50 | Demo 與總結 | 控制分享品質與回饋節奏 | 每組都要有可展示內容 |

### 3.3 上午場控法

上午的成功標準不是每個人都完全理解 Hermes 的所有設計，而是大部分學員都能完成三件事：

- 成功進入可操作環境。
- 跑出至少一個可觀察的任務結果。
- 理解 Hermes 會怎麼串接工具與流程。

上午如果卡住，優先保住操作進度，再補概念。不要反過來。

### 3.4 下午場控法

下午的成功標準不是做出產品，而是每組都能在既定場景下完成「需求、原型、修正、展示」四步。

講師要持續提醒各組：

- 不要自己加題。
- 不要一開始就追求最完整方案。
- 每 20 分鐘至少做一次可運作驗證。
- Demo 要能說清楚場景、流程、結果與限制。

## 四、每個 Lab 的講師重點

### Lab 1：Hermes 安裝與基礎操作

**講師目標**：讓每位學員至少完成安裝、啟動、第一次任務。

**講師重點**：

- 先示範完整流程一次，再拆步驟帶學員做。
- 不要同時講太多背景知識，先讓畫面跑起來。
- 第一個任務要選低風險、容易看懂結果的內容，例如整理一段工作筆記。
- 現場若有人安裝失敗，請助教接手；主講師繼續帶大隊前進。

**完成標準**：

- 學員能看到 Hermes 有輸入、有執行、有輸出。
- 學員知道失敗時先看哪裡，不會完全停住。

### Lab 2：工具系統深度探索

**講師目標**：讓學員知道工具的價值在於補足模型能力，而不是炫技。

**講師重點**：

- 用任務情境帶工具，不要先堆工具名單。
- 每增加一種工具，都要講清楚它解決了什麼限制。
- 特別提醒最小權限原則，避免學員把所有工具全開。
- 帶學員比較「不用工具」與「用工具」的結果差異，讓差異被看見。

**完成標準**：

- 學員能完成至少一個多步驟任務。
- 學員能說出為什麼這個任務需要兩種以上工具。

### Lab 3：自動化流程與自學習迴圈

**講師目標**：讓學員理解 Agent 的價值不只是一問一答，而是能形成可重複的工作流。

**講師重點**：

- 不要把這段講成理論課，要讓學員看到重複任務的差異。
- 引導學員觀察「第一次做」和「第二次做」的差別。
- 若現場時間吃緊，先保住排程或流程串接示範，再談自學習細節。
- 幫學員把工作流寫成一句明確任務，避免描述過散。

**完成標準**：

- 學員能描述一個可重複執行的流程。
- 學員理解為什麼這類流程適合交給 Agent。

### Lab 4：辦公室場景實作（一）— 從需求到原型

**講師目標**：讓各組在有限時間內完成第一版可運作原型。

**講師重點**：

- 場景選擇後，先要求各組用一句話定義成果。
- 提醒各組把需求拆成「輸入、處理、輸出」三段。
- 若組別陷入長時間討論，直接要求先做最小版本。
- 幫各組盯住測試資料品質，避免用太亂的資料把自己卡死。

**完成標準**：

- 各組至少有一條成功跑完的流程。
- 各組知道目前版本的限制是什麼。

### Lab 5：辦公室場景實作（二）— 迭代與優化

**講師目標**：讓各組學會修正、收斂、補強，而不是一直重做。

**講師重點**：

- 先要求各組列出一個最想修的問題，不要同時改五件事。
- 把優化分成三類：提示詞、工具配置、流程順序。
- 若組別一直在試錯，請他們保留一個可用版本，不要把唯一成果改壞。
- 提醒各組開始準備 Demo，不要等最後十分鐘才整理說法。

**完成標準**：

- 各組有一版比 Lab 4 更穩定或更完整的成果。
- 各組能清楚說明「改了什麼，為什麼要改」。

### Lab 6：分組挑戰賽 — 跨場景整合

**講師目標**：讓學員感受到 Agent 能力可以組合，但不讓挑戰賽破壞主線成果。

**講師重點**：

- 先講清楚這是延伸挑戰，不是必做主線。
- 題目要小而明確，避免變成新專案。
- 對進度落後的組別，可以允許只講整合構想，不必強求完整做出來。
- 對進度超前的組別，鼓勵他們把整合價值講清楚，而不是只展示功能數量。

**完成標準**：

- 各組至少能提出一個跨場景整合思路。
- 有餘力的組別能做出簡化版整合示範。

## 五、巡場策略

### 5.1 巡場原則

巡場不是逐桌回答所有問題，而是先辨識問題類型，再決定要個別處理還是全班同步提醒。

### 5.2 建議巡場分層

| 類型 | 特徵 | 處理方式 |
|------|------|----------|
| 環境卡點 | 安裝、權限、API、網路 | 交給助教優先處理 |
| 操作卡點 | 不知道下一步、看不懂輸出 | 講師或助教口頭點一下即可 |
| 任務設計卡點 | 題目太大、需求太散 | 講師協助收斂範圍 |
| 小組協作卡點 | 分工不清、沒人決定方向 | 講師指定一位窗口負責整合 |

### 5.3 巡場節奏建議

- Lab 1 以排除環境問題為主。
- Lab 2、Lab 3 多看學員是否真的理解工具與流程的關係。
- Lab 4 之後優先巡進度最慢與方向最散的組。
- 每次巡場最多花 3～5 分鐘，避免被單一組別綁住。

### 5.4 巡場時可直接問的四句話

1. 你們現在卡的是環境、流程，還是需求？
2. 你們這一版的輸入、處理、輸出分別是什麼？
3. 如果只能留一個功能，要留哪一個？
4. 你們下一個 10 分鐘要驗證什麼？

## 六、常見卡點與排除方式

| 卡點 | 現場表現 | 建議處理 |
|------|----------|----------|
| 安裝失敗 | 少數學員一直停在環境設定 | 助教接手，必要時切到備用環境 |
| API 無法使用 | 額度不足、金鑰錯誤、權限受限 | 先換備用金鑰，課後再處理個人帳號 |
| 網路不穩 | 請求很慢或反覆失敗 | 切手機熱點，或改用講師共用示範 |
| 工具沒有如預期被用到 | 學員以為設定了就一定會觸發 | 回到任務描述，重寫更明確的指令 |
| 任務做太大 | 小組一直討論，不產出結果 | 改成最小版本，只保留一條主流程 |
| 輸出不穩定 | 每次結果差很多 | 縮小輸入範圍、固定資料格式、減少任務變數 |
| Demo 前還在改 | 成果不穩，無法展示 | 立即凍結版本，只整理講法與流程 |

### 補充原則

- 環境問題不要在全班面前修太久。
- 若超過 5 分鐘還排不掉，先讓該學員接到備援流程。
- 排障時優先保住課程節奏，不追求現場把所有個案修到最好。

## 七、時間管理建議

### 7.1 講師要守住的時間點

- 09:25 前一定完成開場與分組。
- 10:10 前大部分學員要完成第一次任務。
- 12:10 前大部分學員要看過工具與流程串接。
- 14:10 前每組要選定場景並做出第一版原型。
- 15:10 前每組要進入優化或整理 Demo。
- 16:10 前所有組別都要停止開發，準備展示。

### 7.2 常見失控點

#### 開場太長

如果講太多背景，後面所有 Hands-on 時間都會被壓縮。開場只要講目標、規則、成功標準，不要重講完整理論。

#### 安裝段落拖太久

Lab 1 最容易吃掉整天節奏。主講師不能陪著少數學員逐步排錯，這會讓已完成的學員開始失焦。

#### 下午分組太自由

若沒有明確里程碑，各組會在需求討論中空轉。講師要定時廣播「現在應該完成到哪裡」。

### 7.3 廣播節點建議

建議在以下時間點做全班廣播提醒：

- 每個 Lab 開始後 10 分鐘：確認大家知道當前目標。
- 每個 Lab 中段：提醒剩餘時間與最低完成標準。
- 每個 Lab 結束前 5 分鐘：要求停下來驗證與整理。

## 八、Demo 與回饋方式

### 8.1 Demo 安排原則

Demo 不是比誰功能最多，而是比誰最清楚說明問題、做法、結果與限制。

### 8.2 每組 Demo 建議格式

每組控制在 5 分鐘內，建議順序如下：

1. 場景與痛點。
2. 這組做了什麼。
3. 實際跑一次或展示結果。
4. 哪裡成功，哪裡還沒解決。
5. 如果再多 1 小時，下一步會做什麼。

### 8.3 講師回饋框架

講師回饋可以固定用三段：

- 先指出這組最清楚的價值。
- 再指出一個最值得優先改進的地方。
- 最後補一句這個做法帶回工作現場時要注意什麼。

### 8.4 同儕回饋方式

可請其他學員用以下角度給回饋：

- 這個場景是否真的有工作價值？
- 這個流程最容易出錯的地方在哪裡？
- 如果放到自己部門，會想先拿去哪個任務試？

### 8.5 收尾時要講清楚的三件事

- 今天完成的是原型，不是正式上線方案。
- 真正帶回工作現場前，還要補資料治理、權限與驗證機制。
- 只要先守住小場景、固定輸入、可重複流程，Agent 才有機會穩定落地。

## 九、課後建議

### 9.1 對學員的課後建議

- 先把今天做的場景縮小成自己工作中一個固定任務。
- 在一週內重做一次，確認不是只在課堂資料上可用。
- 保留提示詞、流程與測試資料，方便後續迭代。
- 若要在公司內部推廣，先從低風險、可回溯的任務開始。

### 9.2 對講師的課後建議

- 整理哪些卡點最常出現，回頭修正課前通知與教材。
- 記錄各組最常選的場景，觀察哪些題目太難或太散。
- 收集學員 Demo 截圖或成果摘要，作為下次教學案例。
- 檢查哪些段落講太久、哪些段落時間不足，下次直接調整。

### 9.3 建議追蹤項目

若後續有進階班或社群活動，可追蹤：

- 學員是否在課後兩週內再次使用 Hermes。
- 哪一類辦公室場景最容易實際落地。
- 學員最常遇到的是環境問題、流程問題，還是場景定義問題。
